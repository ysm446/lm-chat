# Document RAG の仕組み

LM Chat の Document RAG は、ワークスペースに取り込んだ文書をチャンク化し、  
会話時に関連部分だけを検索してプロンプトへ追加する仕組みです。

毎回文書全文を渡すのではなく、次の流れで必要部分だけを使います。

1. 文書を取り込む
2. 文書をチャンク化する
3. 各チャンクを embedding して保存する
4. ユーザー入力をクエリにして関連チャンクを検索する
5. 上位チャンクだけを補助コンテキストとして LLM に渡す

---

## 1. 何をクエリにして検索するか

Document RAG の検索クエリは、基本的に「今回の最後のユーザー入力文」です。

- 通常送信時は `payload.content`
- その文字列を embedding モデルでベクトル化して検索ベクトルを作る
- 同時に、その文字列をそのまま全文検索にも使う

つまり、

- 保存されている文書: 取り込まれたファイルから作られた文書チャンク
- 検索クエリ: 今回のユーザー質問文

という構成です。

---

## 2. 対応ファイル形式

現在の実装で扱うファイル形式は次の 3 つです。

- `.txt`
- `.md`
- `.json`

`/documents` への取り込み時、この 3 形式以外は受け付けません。

---

## 3. 文書の取り込み時に何をするか

文書の取り込み時は、次の処理を行います。

1. ワークスペース配下にファイル本体を保存する
2. `documents` テーブルにメタ情報を保存する
3. バックグラウンドスレッドで文書をチャンク化する
4. 各チャンクを `document_chunks` に保存する
5. 全文検索用の `document_fts` に保存する
6. ベクトル検索用の `document_vec` に embedding を保存する
7. 完了時に `indexed_at` を更新する

ファイル本体は次の場所に保存されます。

```text
data/assets/documents/{workspace_id}/{file_name}
```

---

## 4. チャンク分割

文書のチャンク分割は `backend/documents/chunker.py` で行っています。

現在の基本パラメータは次の通りです。

- 目標サイズ: `400` 文字
- 最大サイズ: `500` 文字
- オーバーラップ: `50` 文字

長いチャンクは、改行や句読点、スペースを優先して分割します。  
どうしても自然な区切りが見つからない場合は、最大文字数で強制分割します。

---

## 5. 形式ごとのチャンク化

### `.txt`

プレーンテキストは、まず空行区切りの段落単位でまとめます。  
その結果が長すぎる場合だけ、さらに 500 文字以内に分割します。

### `.md`

Markdown は見出し行 `#` を一次境界として使います。

- 見出し単位のセクションを作る
- セクションが短ければそのまま 1 チャンクにする
- 長い場合は本文をさらにテキスト分割する
- 最初のサブチャンクには見出しを付け直す

つまり、Markdown は見出し構造をなるべく保ったままチャンク化されます。

### `.json`

JSON はまずパースを試みます。

- オブジェクトならトップレベルキーごと
- 配列ならトップレベル要素ごと
- それぞれを整形済み JSON 文字列にしてまとめる

長すぎる場合だけ追加分割します。  
JSON として読めなかった場合は、プレーンテキストと同じ分割にフォールバックします。

---

## 6. 全文検索

全文検索には SQLite の `FTS5` を使っています。

流れは次の通りです。

1. クエリ文字列を `"..."` で囲んでフレーズ検索用にする
2. `document_fts` に対して `MATCH` を実行する
3. 同じ `workspace_id` のチャンクだけに絞る
4. 上位 `top_k * 4` 件を候補として取る

ヒットしたチャンクには、順位に応じて次の加点をします。

```text
fts_score = 1 / (rrf_k + rank + 1)
```

- `rrf_k = 60`
- `rank` は 0 始まり

全文検索のスコアも、距離ではなく順位ベースです。

---

## 7. ベクトル検索

ベクトル検索には `sqlite-vec` を使っています。

流れは次の通りです。

1. ユーザー入力文を embedding モデルでベクトル化する
2. そのベクトルで `document_vec` に KNN 検索をかける
3. まず `top_k * 4` 件の近傍候補を取る
4. その後で `workspace_id` に一致するチャンクだけに絞る

ベクトル検索でも、順位に応じて次の加点をします。

```text
vector_score = 1 / (rrf_k + rank + 1)
```

ここでも `rrf_k = 60` です。

---

## 8. 全文検索とベクトル検索の統合

各文書チャンクごとに、全文検索とベクトル検索の加点を足し合わせます。

```text
merged_score = fts_score + vector_score
```

つまり、

- 全文検索だけでヒットしたチャンク
- ベクトル検索だけでヒットしたチャンク
- 両方でヒットしたチャンク

がありえます。

両方でヒットしたチャンクは、その分だけ上位に来やすくなります。

---

## 9. 最終的な採用

統合スコアの高い順に並べ替え、上位 `top_k` 件を採用します。  
現在 `build_document_context()` では `top_k = 3` を使っています。

採用されたチャンクは、文書ごとにファイル名ラベルを付けて次のような形でまとめられます。

```text
## ワークスペース資料から検索された関連情報
以下はワークスペースに登録された資料から自動検索された情報です。

[参照資料: rules.md]
...

[参照資料: spec.txt]
...
```

この文書コンテキストは、そのまま LLM に渡される補助情報になります。

---

## 10. 記憶検索との結合

Document RAG は単独ではなく、既存の記憶検索と一緒に使われます。

現在の実装では、まず

- 文書コンテキスト
- 会話メモリコンテキスト

の順で結合します。  
さらに合計文字数がおおむね `2000` 文字を超えないように切り詰めます。

つまり、現状では文書側が先に優先される設計です。

---

## 11. UI 上の扱い

現在の UI では、ワークスペース配下に `Documents` セクションがあります。

- `.txt` / `.md` / `.json` を追加できる
- 取り込み後は一覧表示される
- 項目をクリックすると中央ペインで内容を開ける
- 内容編集、リネーム、削除ができる
- 保存時は再インデックスされる

インデックス中は `indexed_at = null` で扱われ、完了後に時刻が入ります。

---

## 12. 現在のスコープと制約

データモデル上は `scope` と `session_id` を持っていますが、現在の実装は実質的に **ワークスペース資料中心** です。

現状の挙動:

- 一覧取得は `workspace` スコープのみ
- 検索も `workspace_id` 単位で行う
- セッション限定文書の注入フローはまだ本格利用していない

つまり、今の Document RAG は「ワークスペース共通資料を検索して会話に足す機能」と考えるのが正確です。

---

## 13. まとめ

現在の Document RAG は、次の考え方で動いています。

- クエリは最後のユーザー質問文
- 文書は取り込み時にチャンク化・埋め込みされる
- `.txt` / `.md` / `.json` を形式ごとに分けてチャンク化する
- 全文検索とベクトル検索を両方走らせる
- 順位ベースの加点で両者を融合する
- 上位 3 チャンクだけを資料コンテキストとしてプロンプトに入れる
- 記憶検索コンテキストと合わせて、合計約 2000 文字以内で使う

要するに、

- キーワードとして近い
- 意味として近い
- しかもワークスペース内の資料に含まれている

という文書断片を、会話時に補助知識として差し込む設計です。
