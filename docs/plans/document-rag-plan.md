# 文書RAG機能の計画メモ

Local LLM Chat にはすでに「過去会話をチャンク化し、埋め込み検索して system prompt に足す」記憶検索の土台があります。  
このメモでは、その延長として **文書ファイルを取り込み、ワークスペース単位または会話単位で参照できる RAG 機能** を追加する場合の方針を整理します。

---

## 1. この機能でやりたいこと

追加したい文書RAGは、大きく次の 2 系統です。

### A. ワークスペース資料

- PDF / txt / md などの文書をワークスペースに紐づけて保存する
- 同じワークスペース内の複数チャットから共通で参照できる
- いわば「このワークスペース専用の知識ベース」

### B. 会話限定の添付資料

- チャット送信時に画像のように文書を添付する
- その会話だけで検索対象に含める
- ワークスペース全体には共有しない

この 2 つは検索対象も保存寿命も違うため、UI とデータ構造の両方で区別したほうが扱いやすい。

---

## 2. 基本的な考え方

文書RAGは、毎回文書全文を system prompt の後ろに付ける方式ではありません。  
流れは次のようになります。

1. 文書を取り込む
2. テキストを抽出する
3. テキストをチャンクに分割する
4. 各チャンクの embedding を保存する
5. ユーザー質問時に関連チャンクだけ検索する
6. その一部だけを system prompt 側へ追加して LLM に送る

つまり、LLM 自体に RAG が内蔵されるというより、**バックエンドが外部知識を検索して補助コンテキストを組み立てる** 形になる。

---

## 3. 保存場所の方針

画像添付と同様に、文書本体は DB に直接入れず **外部ファイルとして保存** するのが自然です。  
一方で、検索のためのメタ情報・チャンク・embedding は DB 側で管理します。

### 保存の分離

- 文書本体
  - 例: `data/assets/documents/{workspace_id}/...`
  - 会話限定添付なら `data/assets/documents/{workspace_id}/{session_id}/...`
- メタ情報
  - ファイル名
  - MIME type
  - サイズ
  - ハッシュ
  - 取り込み日時
  - 所属スコープ
- チャンク
  - 抽出テキストの分割単位
- embedding
  - チャンクごとのベクトル

要するに、

- 本体ファイルは外に置く
- 検索インデックスは DB に持つ

という画像添付に近い設計がよさそうです。

---

## 4. スコープ設計

文書には「誰が見えるか」の単位が必要です。  
最低限、次の 2 スコープを持たせたいです。

### workspace スコープ

- ワークスペース配下の共通知識
- そのワークスペースの全チャットから検索対象にできる

### session スコープ

- その会話専用の添付資料
- 添付したセッションでのみ検索対象にする

必要なら将来的に `message` スコープを追加し、どのメッセージの添付かまで追跡できるようにしてもよいです。

---

## 5. 取り込み時の流れ

文書のインポート時には、次の前処理が必要です。

1. ファイル本体を保存する
2. テキストを抽出する
3. 不要な改行やノイズを整形する
4. チャンク分割する
5. embedding を計算する
6. DB にメタ情報・チャンク・ベクトルを保存する

### チャンク分割の考え方

- まず見出し・段落・改行などの自然な区切りを優先する
- 長すぎる部分だけ文字数またはトークン数で追加分割する
- 文脈切れを防ぐため、少し overlap を入れる

PDF はそのままきれいな文章にならないことも多いため、  
「PDF を直接分割する」というより **抽出後の整形済みテキストを分割する** と考えたほうがよいです。

---

## 6. 検索時の流れ

ユーザーが質問を送ったら、次の順序でコンテキストを組み立てるイメージです。

1. 会話メモリ検索
2. ワークスペース資料検索
3. 会話限定添付資料検索
4. それぞれの上位チャンクをまとめる
5. system prompt の後ろへ補助コンテキストとして追加する

このとき、検索結果は無制限に足さず、件数や文字数の上限を持たせる必要があります。

---

## 7. UI の置き場所

資料の追加導線は、用途ごとに 2 か所へ分けるのが自然です。

### A. ワークスペース資料

置き場所はサイドバーのワークスペース配下がよいです。

イメージ:

```text
Workspace A
  chat 1
  chat 2
  Documents
    rules.pdf
    spec.txt
```

ポイント:

- チャットは今まで通りワークスペース直下に並べる
- `Documents` だけを補助セクションとして追加する
- 情報設計上は同じワークスペース配下の資産として見せる
- `Documents` セクションから追加・削除・再インデックスを行う

### ワークスペース資料をクリックしたときの扱い

`rules.pdf` のような資料項目をクリックした場合は、中央エリアにその文書の詳細を表示するのが自然です。

想定する内容:

- ファイル名
- 取り込み日時
- サイズ
- 検索対象かどうか
- 再インデックス
- 削除
- 抽出テキストのプレビュー
- 可能なら元ファイルの簡易プレビュー

つまり、文書項目は「チャットを開く」のではなく、**資料の詳細ビューを中央エリアに開く** イメージです。

最初の実装では、無理に高機能な PDF ビューアを作らず、

- メタ情報表示
- 抽出テキストのプレビュー
- 操作ボタン

だけでも十分です。

### B. 会話限定の添付資料

置き場所はメッセージ入力欄の添付 UI がよいです。

- 画像添付と同じ操作感で文書も添付できる
- その添付文書は current session だけの検索対象にする
- 「この PDF を見ながら答えて」という用途に向く

要するに、

- 永続資料はワークスペース側
- 単発資料は入力欄添付

という住み分けがもっとも分かりやすいです。

---

## 8. データ構造の最小案

既存の `memory_chunks` を流用する方法もありますが、意味の違いを考えると文書用テーブルを分ける案がわかりやすいです。

### documents

- `id`
- `workspace_id`
- `session_id` nullable
- `message_id` nullable
- `scope` (`workspace` / `session`)
- `file_name`
- `mime_type`
- `file_path`
- `file_size`
- `file_hash`
- `created_at`

### document_chunks

- `id`
- `document_id`
- `workspace_id`
- `session_id` nullable
- `chunk_index`
- `content`
- `created_at`

### document_vec

- `chunk_id`
- `embedding`

全文検索も今の `memory_fts` と同様に、文書チャンク用の FTS テーブルを持たせると扱いやすいです。

---

## 9. embedding model の方針

初期実装では、既存の記憶検索と同じ embedding model を使うのが安全です。  
現在の実装では `ruri-v3-310m` を使っているため、文書RAGでもまずはこれに揃える方針が自然です。

理由:

- 同じ検索用途では、文書チャンクと検索クエリを同じベクトル空間に置く必要がある
- 会話メモリ検索と文書検索で設計を揃えやすい
- 実装や運用が単純になる

注意点:

- 別モデルを使う場合は、インデックスを分けるか再インデックス前提の設計が必要
- 将来 embedding model を切り替える可能性を考えると、モデル名やバージョンをメタ情報として持てるようにしておくとよい

要するに、最初は **既存の `ruri-v3-310m` を流用する** のがおすすめです。

---

## 10. 実装方針の候補

### 案1. まずはワークスペース資料だけ実装する

利点:

- 概念が単純
- UI もサイドバーに集約できる
- 文書RAGの基本機能を先に固めやすい

欠点:

- 「この会話だけで見てほしい PDF」用途にはまだ弱い

### 案2. まずは会話添付だけ実装する

利点:

- 画像添付 UI の延長で実装しやすい
- ユーザーの体験がわかりやすい

欠点:

- ワークスペース共有知識として再利用できない

### 案3. 両方を見据えて基盤だけ先に共通化する

おすすめはこの案です。

1. 文書保存とチャンク管理の基盤を作る
2. スコープとして `workspace` / `session` を持たせる
3. 先に UI はどちらか片方から出す

これなら後から片方を足しても設計が崩れにくいです。

---

## 11. 初期実装のおすすめ

最初の一歩としては、次の順が現実的です。

1. 文書メタ情報 + チャンク + embedding 保存のバックエンドを追加
2. ワークスペース配下に `Documents` セクションを追加
3. PDF / txt / md のインポートを実装
4. 検索結果を system prompt に足す流れを追加
5. その後で会話限定添付を `session` スコープとして追加

この順にすると、

- データ設計
- 検索設計
- UI

を無理なく積み上げられます。

---

## 12. まとめ

今回の方針を短く言うと次の通りです。

- 文書RAGは、既存の会話メモリ検索の延長として実装できる
- 文書本体は外部保存、検索用データは DB 保存が自然
- スコープは少なくとも `workspace` と `session` を分けたい
- UI は「ワークスペース資料」と「会話添付」で導線を分ける
- サイドバーでは `Chats` と `Documents` をワークスペース配下の別セクションとして並べる

この方針なら、将来

- ワークスペース知識ベース
- 会話限定の添付RAG
- 文書の再インデックス
- 参照元表示

まで比較的素直に拡張できそうです。
