## 構想: ライブラリ（データルート）切り替え

Obsidian の vault に近い形で、アプリが開く「ライブラリ（データルート）」を切り替えられるようにする構想。

### 決定事項（2026-07-07）

- **実体フォーマット: フォルダ方式で実装する**（第一案）。`library.db` 1 ファイル化は将来の発展課題として温存。

#### ライブラリ / 環境の線引き（確定）

判断基準: **マシン依存の値＝環境設定、作品ごとに変えたい値＝ライブラリ設定**。

- **ライブラリ側（切り替え単位。フォルダごとコピー可）** = 実質この4点:
  - `lm_chat.db`（本体）
  - `assets/{images,documents}/`（DB 行が参照する実体。DB と一心同体）
  - `system_prompts.json`（作品ごとのプロンプト）
  - 作風・RAG チューニング設定: `temperature`・`completion_length`・`memory_scope`・`memory_context_*`・`document_*` 等（旧 `config.json` から分離した `library_config.json`）
- **環境側（アプリ/マシン共通。ライブラリの外、`~/.lmchat/` 等）**:
  - `llama_paths.json`（マシン固有: 絶対 exe/model パス・PID・runtime variant。ライブラリに入れない）
  - UI 設定（旧 `settings.json`: フォント・解像度・サイドバー開閉・debug フラグ）
  - `runtime/`・`models/`（現在地のまま）
  - アクティブライブラリへのポインタ・最近開いたライブラリ一覧
- **ハード設定は環境側に一本化（確定）**: `n_gpu_layers`・`ctx_size` は環境(Runtime)へ。
  - ⚠️ 既存負債の解消: `n_gpu_layers` は現状 `config.json` と `llama_paths.json` に**二重**。環境側に一本化する。
  - `ctx_size` は現状 右サイドバー Context セクション（会話中に触る扱い）にあるが、マシン依存なので環境(Runtime)へ寄せる。
- **要注意の分割**: `settings.json` の `sidebar_expanded_workspace_ids` / `sidebar_expanded_document_workspace_ids` は DB 内の workspace ID を参照する。環境側に残す場合は「存在しない ID は無視する寛容読み」にするか、ライブラリ側へ移す。

#### 設定 UI の分離（確定）

既存の二面構成（右サイドバー＝生成コントロール / 設定ウインドウ＝アプリ設定）が、偶然ながらライブラリ/環境の軸とほぼ一致している。新規 UI は作らず、**既存二面を『ライブラリ設定』『環境設定』として明示ラベル化**する。

- 目的: 「この設定はライブラリを切り替えたら付いてくるのか？」というユーザーの不安を UI 上で解消する。
- 設定ウインドウ左ナビを2グループ見出しに割る:
  - **環境設定（このPC）**: Interface / Model / Runtime / Debug（「全ライブラリ共通」と明記）
  - **ライブラリ設定（現在のライブラリ）**: System Prompt / 作風系 config / RAG(Memory・Documents)（アクティブなライブラリ名を添える）
- 現在開いているライブラリ名を常時表示（切り替え UI と兼ねる）。
- **スキーマ移行方式: `PRAGMA user_version` を導入する**。現状の冪等 init（`CREATE IF NOT EXISTS` / `ALTER ADD COLUMN` の try/except）は前方追加専用で、列削除・リネーム・データ変換を表現できない。ライブラリは「かなり古いものを久しぶりに開く」状況が本番より起きやすいため、順序つき移行を扱える仕組みが要る。
  - 冪等 init は残す（単純な列/テーブル追加は今まで通りこれで足りる）。
  - `user_version` は **データ変換を伴う移行だけ** を拾う。起動時に「DB の版 < アプリが期待する版」なら版 N→N+1 の移行関数を昇順適用し版を上げる。先日の Ruri v3 再埋め込みのような一回限りスクリプトも、この枠組みに載せれば「開けば自動で追いつく」に統合できる。
  - 古すぎる / 新しすぎるライブラリは版番号で安全に弾く（「このライブラリはこのアプリで開けません」）。
  - 移行は `store_base._init_db()` 内（DB を開いた瞬間）で走らせる。ライブラリ切り替え＝新しい DB パスで Store を作り直す実装にすれば、切り替え時に自動で最新スキーマへ追従する。

- 階層: ライブラリ（フォルダ＝開く単位、完全分離）の中に既存のワークスペース（DB 内、文脈分離）が入る。**ワークスペースは廃止せず温存**し、フォルダ分離とは役割を分ける。
- 利点: 用途ごとに完全独立した DB を持てて記憶の混入が起きない。フォルダを丸ごとコピーするだけでバックアップ/移動できる。既存のワークスペース ZIP エクスポート/インポートは「ライブラリ間で 1 ワークスペースだけ移す」用途として残る。
- 同時に開くのは 1 ライブラリのみとする想定（横断検索は諦め、分離を優先）。
- 実装時にまず決めること:
  - **ライブラリ単位 / アプリ共通の線引き**（最重要）。ライブラリ側候補: `lm_chat.db`・`assets/`・`system_prompts.json`・`config.json`。アプリ共通候補: `runtime/`・`models/`・`llama_paths.json`・UI 設定（`show_left/right` 等）。
  - 起動時に解決する単一の `DATA_ROOT` へパスを集約する（現状は `data` がハードコード: `store_base.py`・`config_store.py`・`settings_store.py`・`routes/deps.py`・`memory/db.py` 等）。アクティブライブラリのパスは `~/.lmchat/active` のような小さなポインタファイルで保持。
  - 切り替え UI（最近開いたライブラリ、開く/作成）と、切り替え時のバックエンド再初期化の扱い。
- **発展構想: ライブラリ＝1 ファイル化（SQLite をコンテナとして使う）**。フォルダではなく `library.db` 1 個でライブラリを表現する案。圧縮アーカイブ（zip/tar）と違い展開不要で直接読み書きでき、コピー/移動/バックアップが OS のファイルコピー 1 回で完結する。SQLite 開発元自身が「アプリケーションファイルフォーマット」として推奨する使い方。
  - やること: 周辺のサイドカーファイルを核の DB に吸収する。`config.json`・`system_prompts.json` → テーブル行に畳む。`assets/`（画像・文書本体）→ BLOB テーブルに格納し、読み書きを「ファイルパス経由」から「DB BLOB 経由」に通す。
  - トレードオフ: ①稼働中は WAL の `-wal`/`-shm` が脇にでき厳密には 1 ファイルでない（クリーンに閉じれば `library.db` 1 個に戻る）。②文書を外部エディタで直接編集できなくなる（本アプリは `DocumentEditor` 編集前提なので実害は小さい）。③削除した BLOB 領域は自動で縮まず時々 `VACUUM` が要る。④Windows には macOS バンドルのような「フォルダを 1 ファイルに見せる」OS 機能がないため、1 ファイル化するならコンテナ形式が必須で SQLite が最も素直。
  - 線引きの論点: **assets を BLOB に完全格納（真の 1 ファイル優先）か、DB はメタデータのみ持ち実体はサブフォルダに残す（外部編集性・差分バックアップ優先）か**。完全 1 ファイルと文書の外部編集性はトレードオフ。

## 構想: 生成メッセージのバージョン管理

再生成したアシスタント応答を版として保持し、以前の版に戻せるようにする構想。

- 現状: 再生成は `store.replace_message()`（`routes/chat.py`）で**上書き＝破壊的**。旧版は消える。
- 方式: `message_versions` テーブルを追加し、`messages` 行は常にアクティブ版を保持（既存の読み取りコードは変更不要）。過去の版を `message_versions` に退避する。
  - 列イメージ: `id` / `message_id` / `content` / `completion_tokens` / `tokens_per_second` / `elapsed_seconds` / `finish_reason` / `model_name` / `created_at` / `version_index`。`_init_db()` の ALTER/CREATE で自動マイグレーション。
  - 再生成時: 上書き前に旧 content を版として退避し、新版も記録。
  - 切替時: `messages.content` を選択版へ差し替え＋セッション記憶を再構築（既存の再生成処理を流用）。
- UI: アシスタントメッセージに `‹ 2/3 ›` 形式のページャ（`ChatView.tsx` のアクションボタン群付近）。`chatStore` に版取得/切替アクション、`api.ts` にクライアント関数。
- 新エンドポイント: `GET .../messages/{id}/versions`、`POST .../messages/{id}/active-version`、版削除用の `DELETE .../messages/versions/{id}`。
- **版が増え続けないように個数制限と削除を入れる**:
  - 保持上限（例: 直近 N 版）を設け、超過分は古い版から自動削除。
  - 不要な版を手動削除できる UI。
- データ量: 版はテキスト行のみ（画像 `image_data` は再生成対象外）で 1 版あたり数 KB 程度。実質ほぼ無視できる。上限はデータ量対策というより UI/整理目的。
- 決めること: 編集（PATCH メッセージ）も版として扱うか（まずは再生成のみに絞るのが手堅い）。上限の既定値。
